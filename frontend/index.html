Twelve lessons in database design

Every lesson explains one idea a database designer is expected to know, shows a worked schema and ends with questions you can answer yourself. When you have read one, press Open in Reviewer to send its example through the audit and watch the rules being applied.

1 The relational model and the key ladder Foundations

By the end you can say what a relation is, and how a superkey, a candidate key, a primary key and an alternate key differ.

A table is a relation: a set of rows, each row a set of values drawn from the column's domain. Because it is a set, two rows can never be identical, and the order of rows or columns carries no meaning. Every other rule in this section exists to keep that promise while many people change the data at the same time.

  • A superkey is any set of columns that identifies a row. A candidate key is a superkey with no spare column in it. The primary key is the candidate key you nominate; the others become alternate keys.
  • Entity integrity is the rule that the primary key is unique and never NULL. Without it a row cannot be addressed, so nothing can reference the table reliably.
  • Every non-key column must describe the key, the whole key, and nothing but the key — the one-line summary of 2NF and 3NF that you will meet again in lessons 4 to 6.
CREATE TABLE student (
  student_id INT PRIMARY KEY,
  full_name VARCHAR(100) NOT NULL,
  date_of_birth DATE
);

Check yourself

Is every candidate key also a superkey?

Yes. A candidate key is defined as a minimal superkey, so it identifies a row like any superkey — it simply has no removable column.

Why is a missing primary key a warning rather than a small suggestion?

Because nothing else can be built on the table: foreign keys need a key to point at, joins need a way to match rows, and without one the same row can be inserted twice.

2 Foreign keys and referential integrity Keys

By the end you can point a foreign key at the right column, and explain what happens when the parent row is deleted.

A foreign key stores another table's key. It is what turns two separate lists of rows into a relationship, and it is the constraint the reviewer treats most seriously: a reference that cannot be resolved is reported as an error, not a hint.

  • The target must be a candidate key of the parent — its primary key or a UNIQUE column — and the two data types must match exactly.
  • A foreign key column may be NOT NULL or nullable, and the difference is a design decision: mandatory (every student belongs to a department) or optional (a task may have no assignee yet).
  • ON DELETE governs the break-up: RESTRICT refuses, CASCADE deletes the children too, SET NULL detaches them. Cascade only where losing the children is genuinely intended.
  • The parent table must be defined in the same script. One file is one universe as far as the review is concerned.
CREATE TABLE department (
  department_id INT PRIMARY KEY,
  department_name VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE student (
  student_id INT PRIMARY KEY,
  full_name VARCHAR(100) NOT NULL,
  department_id INT NOT NULL,
  FOREIGN KEY (department_id) REFERENCES department(department_id)
);

Check yourself

May a foreign key point at a column that is only UNIQUE, not the primary key?

Yes. The standard requires the target to be a candidate key, and a UNIQUE NOT NULL column qualifies. Pointing at the primary key is the habit to keep, because it never moves.

Should every foreign key carry ON DELETE CASCADE?

No. Cascade is right when the children have no meaning without the parent (an order's line items). It is wrong when the children are history or accounts in their own right — RESTRICT makes the deletion fail loudly instead of quietly destroying records.

3 Constraints: NOT NULL, UNIQUE, CHECK, DEFAULT Constraints

By the end you can choose the constraint that makes an illegal row impossible, instead of writing code that hopes it never happens.

Constraints are the cheapest documentation you will ever write: the database enforces them for every reader, every script and every application. Aim for illegal states unrepresentable.

  • NOT NULL — a value is required. Ask of each column: "would a missing value be a bug?" If yes, say so.
  • UNIQUE — no two rows share the value. It does not mean required: NULLs are permitted and most engines allow any number of them, because unknowns are not equal to each other. NOT NULL UNIQUE is how you say "required and distinct".
  • CHECK — a rule over a single row, such as CHECK (marks BETWEEN 0 AND 100) or CHECK (ends_on > starts_on). It cannot look at other rows or other tables; that needs a trigger or the application.
  • DEFAULT records the ordinary case (joined_on DATE DEFAULT CURRENT_DATE) but is not a substitute for NOT NULL.

Exam note: MySQL versions before 8.0.16 parsed CHECK and silently ignored it — a favourite question, because the schema looked right while nothing was enforced. 

CREATE TABLE account (
  account_id INT PRIMARY KEY,
  email VARCHAR(150) NOT NULL UNIQUE,
  display_name VARCHAR(80) NOT NULL,
  is_active BOOLEAN NOT NULL
);

Check yourself

Does UNIQUE stop a second row with the same value if that value is NULL?

No, and that surprises people. Uniqueness compares values, and NULL is the absence of one, so two unknown values do not collide. If the column is important, add NOT NULL.

Where does "a student may not enrol in more than five courses" belong?

Not in a CHECK: the rule spans several rows of the enrolment table. It belongs in a trigger or in the application, and the review will not claim to check it.

4 Functional dependencies and finding the key Normalisation

By the end you can read a set of dependencies, compute an attribute closure, and say which columns form the key.

A functional dependency X → Y says: for one value of X there is at most one value of Y. Written that way, a key is simply a set of columns that determines every other column, and redundancy is a column that many different X's determine.

  • Armstrong's axioms generate every dependency implied by a set: reflexivity (a set determines its own subsets), augmentation (add the same column to both sides) and transitivity (X → Y, Y → Z gives X → Z).
  • The closure X⁺ is everything X determines. Start with X, then repeatedly add the right-hand side of any dependency whose left-hand side is already inside. If X⁺ is every column, X is a superkey; if no smaller set works, X is a candidate key.
  • A dependency is partial when it needs only part of a composite key, and transitive when it runs through a non-key column. Those two words are the whole of 2NF and 3NF.

Worked example: R(A, B, C, D) with A → B, B → C, A → D. Close A: {A} then B, C, D — every column, so A is a superkey and, on its own, the only candidate key. Because B → C has a non-key determinant, R also holds a transitive dependency, so it is not in 3NF. 

CREATE TABLE course (
  course_code VARCHAR(10) PRIMARY KEY,
  course_title VARCHAR(120) NOT NULL,
  credit_hours INT NOT NULL
);

CREATE TABLE course_offering (
  course_code VARCHAR(10) NOT NULL,
  term_code VARCHAR(10) NOT NULL,
  room VARCHAR(20) NOT NULL,
  PRIMARY KEY (course_code, term_code),
  FOREIGN KEY (course_code) REFERENCES course(course_code)
);

Check yourself

If closing X gives every column, what have you found?

That X is a superkey. It becomes a candidate key only if no proper subset of X determines everything — minimality is the difference between the two words.

A → B and B → A hold. How many candidate keys are there?

Two: {A} and {B} are both minimal, since each determines the other and hence everything. You nominate one as the primary key and the other stands as an alternate key.

5 Normalisation I: 1NF, 2NF and 3NF Normalisation

By the end you can spot a repeating group, a partial dependency and a transitive dependency, and decompose them away.

Normalisation removes the redundancy that makes updates dangerous: if a fact is stored twice, one day only one copy gets corrected. Each normal form removes one kind of duplication.

  • 1NF — one value per cell, and no repeating groups. A phone_numbers column holding '555-1, 555-2' is a list, not a value.
  • 2NF — no non-key column depends on only part of a composite key. It can only be violated when the key has more than one column.
  • 3NF — no non-key column depends on another non-key column. Storing building beside department_id is the classic violation, because the building belongs to the department.

Worked decomposition: enrolment(student_id, student_name, course_id, course_title, marks) with the key (student_id, course_id) breaks 2NF twice — student_name depends on student_id alone, course_title on course_id alone. Split them out and the redundancy disappears. 

CREATE TABLE department (
  department_id INT PRIMARY KEY,
  department_name VARCHAR(100) NOT NULL UNIQUE,
  building VARCHAR(60) NOT NULL
);

CREATE TABLE lecturer (
  lecturer_id INT PRIMARY KEY,
  lecturer_name VARCHAR(100) NOT NULL,
  department_id INT NOT NULL,
  FOREIGN KEY (department_id) REFERENCES department(department_id)
);

Check yourself

Can a table with a single-column primary key break 2NF?

No. 2NF asks whether a non-key column depends on part of the key, and a one-column key has no parts. Such a table is in 2NF as soon as it is in 1NF — the interesting test for it is 3NF.

Is a decomposition safe as long as it removes redundancy?

No — it must also be lossless: joining the pieces on the shared key must reproduce exactly the original rows, with none invented and none lost (lesson 6 gives the test).

6 Normalisation II: BCNF, lossless joins and when to stop Normalisation

By the end you can test a decomposition for losslessness, and say why 3NF and BCNF sometimes disagree.

BCNF tightens 3NF with one sentence: every determinant must be a superkey. 3NF tolerates a dependency X → A when A is a prime attribute (part of some candidate key); BCNF does not, which is why a BCNF decomposition can still lose a dependency.

  • Lossless test: split R into R1 and R2 only when R1 ∩ R2 contains a candidate key of at least one of them. Joining back then reproduces R exactly.
  • Dependency preservation: check that every original dependency still holds inside one of the pieces. You can always have lossless joins; you cannot always have lossless plus every dependency — that is the 3NF/BCNF trade-off.
  • When to stop: 3NF is the normal target for transaction systems. Denormalise deliberately — for read-heavy reporting — only with the cost written down: duplicated facts must be updated together.

Classic example: tutor(student, subject, teacher) with (student, subject) → teacher and teacher → subject. The keys are (student, subject) and (student, teacher); since teacher alone is not a superkey, BCNF splits the table — and the first dependency can no longer be expressed. 3NF keeps it and accepts the redundancy. 

CREATE TABLE lecturer (
  lecturer_id INT PRIMARY KEY,
  lecturer_name VARCHAR(100) NOT NULL
);

CREATE TABLE module (
  module_code VARCHAR(10) PRIMARY KEY,
  module_title VARCHAR(120) NOT NULL
);

CREATE TABLE module_tutor (
  module_code VARCHAR(10) NOT NULL,
  lecturer_id INT NOT NULL,
  PRIMARY KEY (module_code, lecturer_id),
  FOREIGN KEY (module_code) REFERENCES module(module_code),
  FOREIGN KEY (lecturer_id) REFERENCES lecturer(lecturer_id)
);

Check yourself

Two tables are split on a column that is not a key on either side. What is the risk?

The join can multiply rows and invent combinations that never existed — the decomposition is lossy. Move a candidate key into the shared overlap first.

Is a denormalised table a mistake?

Not if it is a decision. Keep the normalised tables as the source of truth, copy the data deliberately for reads, and document the refresh rule — the mistake is duplicating facts by accident.

7 From ER model to tables Modelling

By the end you can turn entities, attributes and relationships into a schema without guessing where the foreign keys go.

An ER diagram is a picture of nouns and how they connect; a schema is the same information written as tables. The mapping follows four rules, one per kind of relationship.

  • Entity → table, attribute → column, and the entity's identifier becomes the primary key.
  • 1:N — put the foreign key on the many side. A department has many students, so student.department_id points at department.
  • M:N — neither side can hold the other's key, so the relationship becomes its own table whose primary key is the pair of foreign keys. Attributes of the relationship (the enrolment date, the grade) live there too.
  • 1:1 — a foreign key with UNIQUE on the optional side; weak entities take a composite key made of their owner's key plus their own discriminator.
CREATE TABLE student (
  student_id INT PRIMARY KEY,
  full_name VARCHAR(100) NOT NULL
);

CREATE TABLE course (
  course_id INT PRIMARY KEY,
  course_title VARCHAR(120) NOT NULL,
  credit_hours INT NOT NULL
);

CREATE TABLE enrolment (
  student_id INT NOT NULL,
  course_id INT NOT NULL,
  enrolled_on DATE NOT NULL,
  PRIMARY KEY (student_id, course_id),
  FOREIGN KEY (student_id) REFERENCES student(student_id),
  FOREIGN KEY (course_id) REFERENCES course(course_id)
);

Check yourself

A painter paints many paintings; a painting has one painter. Where does the key go?

On the many side: painting.painter_id references painter. One column, no new table.

Why must the junction table's primary key be the pair?

It stops the same pair being recorded twice — you cannot enrol a student in the same course again — and it gives the relationship itself an identity that child rows can reference.

8 Joins, and what NULL does to a query SQL

By the end you can choose the right join, and explain why a comparison with NULL silently removes rows.

A join combines rows that satisfy a predicate. The join type decides what happens to the rows that do not match, which is usually the part a question is really asking about.

  • INNER JOIN keeps matches only; LEFT JOIN keeps every row of the left table and fills the missing right columns with NULL; FULL keeps both sides; CROSS returns every possible pair, and its row count is the product of the two tables.
  • NULL is not a value, it is the absence of one. Every comparison with it is UNKNOWN, and WHERE keeps only rows that are TRUE — so WHERE x <> 5 quietly drops the rows where x is NULL. Test with IS NULL / IS NOT NULL.
  • NOT IN with a NULL anywhere in the list returns no rows at all, because none of the comparisons is ever TRUE. NOT EXISTS is the safe form.
  • Aggregates skip NULLs: COUNT(*) counts rows, COUNT(col) counts only known values, and AVG(col) divides by the known values only.

Query to try on the schema below: which sales have no note? SELECT sale_id FROM sale WHERE note IS NULL; — then replace IS NULL with = NULL and watch the answer become empty. 

CREATE TABLE customer (
  customer_id INT PRIMARY KEY,
  customer_name VARCHAR(120) NOT NULL
);

CREATE TABLE sale (
  sale_id INT PRIMARY KEY,
  customer_id INT NOT NULL,
  sold_on DATE NOT NULL,
  discount_pct INT,
  note VARCHAR(200),
  FOREIGN KEY (customer_id) REFERENCES customer(customer_id)
);

Check yourself

A LEFT JOIN finds no partner. What appears in the right-hand columns?

NULL for every one of them — which is why a careless WHERE right_column = 'X' turns a left join back into an inner join.

Two tables hold 5 and 4 rows. What can you say about a CROSS JOIN?

It returns exactly 20 rows — every pair — regardless of any matching condition, because there is none.

9 Aggregates, GROUP BY and HAVING SQL

By the end you can summarise a table per group, and say why a filter belongs in WHERE rather than HAVING.

Aggregates collapse many rows into one number. Grouping says per what; the two filters run at different moments in the query, which is the whole reason both exist.

  • Only grouped columns and aggregates may appear in the select list of a grouped query; anything else is ambiguous.
  • WHERE filters rows before grouping; HAVING filters groups after it. So an aggregate condition (COUNT(*) > 2) can only live in HAVING.
  • COUNT(*) counts rows; COUNT(DISTINCT col) counts distinct known values; SUM of no rows is NULL, not zero — wrap it in COALESCE for a report.
  • A window function (SUM(...) OVER (PARTITION BY ...)) gives a per-row running figure without collapsing the rows, which older SQL needed a self-join for.

Query to try on the schema below: revenue per customer, biggest first — SELECT customer_id, SUM(quantity * unit_price) AS revenue FROM sale GROUP BY customer_id ORDER BY revenue DESC; 

CREATE TABLE customer (
  customer_id INT PRIMARY KEY,
  customer_name VARCHAR(120) NOT NULL
);

CREATE TABLE sale (
  sale_id INT PRIMARY KEY,
  customer_id INT NOT NULL,
  quantity INT NOT NULL,
  unit_price DECIMAL(10,2) NOT NULL,
  FOREIGN KEY (customer_id) REFERENCES customer(customer_id)
);

Check yourself

Which filter can test COUNT(*), and when does it run?

HAVING — after the groups have been formed. The same condition in WHERE is rejected, because no aggregate exists yet.

A customer has three rows, one with quantity NULL. What is SUM(quantity)?

The total of the two known values: aggregates ignore NULLs, they do not treat them as zero. If NULL should mean zero, write SUM(COALESCE(quantity, 0)).

10 Indexes and B+ trees Performance

By the end you can explain what an index buys, why it is a tree, and when one is a waste of space.

An index is a second, sorted copy of the values you search by, and most engines keep it as a B+ tree: keys in order, all data pointers in the leaves, and the leaves linked left to right so a range scan can walk them.

  • A node holds hundreds of keys, so the tree stays shallow — three or four levels for millions of rows. A lookup is a few page reads instead of a table scan, which is what O(log n) means in practice.
  • Column order matters. An index on (course_id, student_id) answers questions about course_id alone, but not about student_id alone: the index is sorted by the first column before the second.
  • A covering index contains every column the query needs, so the table is never touched. A clustered index decides the physical order of rows; there is only one.
  • Indexes are not free: each one takes space and slows every insert, update and delete. Index the columns you filter and join on, and skip the ones with few distinct values.

Note: this audit reads table definitions, so it suggests an index for every foreign key whether or not your script declares CREATE INDEX — treat the suggestion as the reminder it is, and add the index yourself as below. 

CREATE TABLE customer (
  customer_id INT PRIMARY KEY,
  customer_name VARCHAR(120) NOT NULL
);

CREATE TABLE invoice (
  invoice_id INT PRIMARY KEY,
  customer_id INT NOT NULL,
  issued_on DATE NOT NULL,
  total DECIMAL(10,2) NOT NULL,
  FOREIGN KEY (customer_id) REFERENCES customer(customer_id)
);

CREATE INDEX idx_invoice_customer ON invoice (customer_id);

Check yourself

Does an index on (a, b) help a query that filters on b only?

No — that is the left-prefix rule. The index is ordered by a first, so it cannot be searched by b alone; you would need a second index beginning with b.

When is a table scan the better plan?

When the query needs a large share of the table, or the column has few distinct values: reading the index and then the rows costs more than reading every page once.

11 Transactions, ACID and concurrency Transactions

By the end you can state the ACID properties, name the three read anomalies, and say what locking guarantees.

A transaction is a unit of work that either completes or leaves no trace. Its four promises — atomicity, consistency, isolation, durability — are what let an application forget about crashes and interleaving.

  • Anomalies appear when transactions interleave: a dirty read reads uncommitted data; a non-repeatable read sees the same row change twice; a phantom sees new rows appear inside a range it already read.
  • Isolation levels trade correctness for concurrency: READ UNCOMMITTED allows all three; READ COMMITTED stops dirty reads; REPEATABLE READ stops non-repeatable reads (the standard still permits phantoms — some engines prevent them anyway); SERIALIZABLE prevents all of them.
  • Two-phase locking takes all its locks before releasing any, and that is enough to guarantee a serializable schedule — at the price of blocking and the occasional deadlock, which the engine resolves by rolling one transaction back.
  • Bank transfers are the standard example: debit and credit must be one transaction, so a reader never sees money that exists nowhere.
CREATE TABLE branch (
  branch_id INT PRIMARY KEY,
  branch_name VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE account (
  account_id INT PRIMARY KEY,
  branch_id INT NOT NULL,
  balance DECIMAL(12,2) NOT NULL,
  opened_on DATE NOT NULL,
  FOREIGN KEY (branch_id) REFERENCES branch(branch_id)
);

Check yourself

Which anomaly does two-phase locking prevent?

All three: every schedule it allows is conflict-serializable, so dirty reads, non-repeatable reads and phantoms cannot be observed.

Why is FLOAT the wrong type for the balance column?

Binary floating point cannot represent values such as 0.10 exactly, so sums of money drift. Use DECIMAL(12,2) / NUMERIC, which stores exact decimal digits.

12 Design hygiene: types, names and one fact per column Practice

By the end you can pick sensible types and names, and recognise the small decisions that are expensive to reverse.

Most "database bugs" are design decisions made early and discovered late. These are the ones that come up again and again in code review — and in the audit on the first page.

  • Types. Money is DECIMAL(p,s), never FLOAT. Time is DATE or TIMESTAMP, never a string. Text is VARCHAR with a realistic limit; CHAR is for fixed-width codes only. Phone numbers and PINs are text, because their leading zeros matter.
  • One fact per column. No address_1_2_or_3, no 'active: yes' stuffed into a status column — and no column that is merely a copy of another table's value.
  • Names you can predict. snake_case, singular table names, *_id for keys, *_at for timestamps, is_/has_ for booleans. The same fact keeps the same name in every table.
  • Room for the future. Add created_at (and updated_at) to anything you may have to audit, and prefer a surrogate key to a natural one that the world can change.
CREATE TABLE customer (
  customer_id INT PRIMARY KEY,
  customer_name VARCHAR(120) NOT NULL
);

CREATE TABLE purchase_order (
  order_id INT PRIMARY KEY,
  placed_on DATE NOT NULL,
  is_paid BOOLEAN NOT NULL,
  customer_id INT NOT NULL,
  FOREIGN KEY (customer_id) REFERENCES customer(customer_id)
);

Check yourself

Why is a surrogate key safer than an email address as the primary key?

People change email addresses, and every child row stores a copy of the key. A surrogate never changes, is narrow, and leaves the email as a UNIQUE column — its real job.

Name three questions to ask about a newly added column.

Can it be NULL — and if so, what does NULL mean here? Which type holds every value it will ever need? Does any other table already store this fact?

How to use this tool — and how to revise with it

Everything a student needs, in one place: the tour, what your results mean, a revision routine, and the answers to the questions that come up.

Start here

  1. Check a schema. Choose one of the sample chips in section I — or paste your own CREATE TABLE statements — and press Review Schema. You get a score, a ranked list of findings, and a diagram of the tables and how they relate.
  2. Design one. In section II, add columns and tick PK / NN / UQ, or point a foreign key at another table. The SQL writes itself; Send to Review Editor hands it straight to section I for checking.
  3. Drill the ideas. Section III offers official GATE PYQs or AI-generated practice. Choose a topic and question count; official questions use the supplied PDF keys, while AI practice includes generated answers and explanations. A wrong answer can be retried until you get it — the score sheet remembers that it took a second attempt.
  4. Practise exam questions. Section IV holds sourced GATE past-paper questions. Pick your answer first, then use Show answer to reveal the key and the reasoning.
  5. Read, then take it away. The twelve lessons in Learn (section V) cover the design rules; Download (section VI) turns them into documents you can print, while History in the command bar reopens earlier reviews.

What your review means

Verdict How to read it
Error Something is broken and will fail in practice — an unresolvable foreign key, for example. Fix these first: the score cannot recover while an error stands.
Warning A rule is missing that you will regret later, such as a primary key or a required column left nullable. These are the ones markers look for.
Suggestion Naming, style and possible redundancy. Worth doing, but they rarely change behaviour.
Passed A check that succeeded. It is listed deliberately, so you can see what was verified rather than assume it.

The score is a weighted summary, not a count of findings: errors cost most, suggestions least, and passing checks add nothing. Two schemas with the same number of findings can therefore score differently — and a design that "works" can still score below 100, because a schema can be correct and badly designed at the same time.

A revision routine that works

  1. Read one lesson, then prove it. Press Open in Reviewer and read which rules the example passed. Answer the self-check questions before you open the answers — retrieval is what makes an idea stick.
  2. Write the schema from memory. Close the lesson and rebuild its example in the Table Designer. When the reviewer scores it well without looking, you own the pattern.
  3. Break it on purpose. Remove a primary key, point a foreign key at the wrong table, make a column nullable — then predict the finding before you press Review. Predicting the verdict is the exam skill.
  4. Mix the topics. Alternate quizzes with exam questions instead of finishing one type. Interleaving feels harder and works better.
  5. Keep a score trail. Export the quiz score sheet after each attempt and watch the "correct after retry" column — it shows what you know and what you are still guessing.

Where your work goes

  • Your SQL, reviews and quiz answers are processed by this site's own server, and reviews and scores are saved in its database so that history and the leaderboard work.
  • Every download is generated in your browser from what is on screen. Nothing is uploaded anywhere by exporting.
  • If the tutor is switched on, only the schema text you submit is sent to the AI service to write an explanation. If it is switched off, the built-in explanations are used and nothing leaves the server at all.

Questions students ask

The status chip says "AI: offline" — is something broken?

No. It means the tutor is unavailable, so explanations come from the built-in material instead. Reviews, scoring, quizzes and exam questions all continue to work, which is exactly why the banks are there.

Why is a foreign key reported as invalid?

The parent table must be defined in the same script and the column it points at must be that table's primary key or UNIQUE. Check the spelling on both sides and the data types — INT must match INT.

Why is a download button greyed out?

Under Your results, a button waits until there is something to save: run a review, design a table, finish a quiz or load exam questions. The line above each button says what is missing. The study material and the practice paper need nothing and are always available.

What does "correct after retry" mean on the score sheet?

You reached the right answer, but not on the first attempt. It is recorded separately because a second-try answer and a known answer are different kinds of knowledge — only the first try earns a point.

Why did my score change when I only renamed a column?

Naming and consistency are checked too. Keep one convention — snake_case, singular table names, *_id keys — and the score settles.

Can I hand in the exported report?

Yes — the review report is a clean record of what was checked. Add a line saying which tool produced it. Exam exports include links to the official papers and answer keys; use those for the original question wording.

Does it work on a phone, or offline?

The layout collapses to a drawer on small screens, so reviewing and quizzing work on a phone. Reading and the built-in banks work without internet; only the optional tutor and the fonts need a connection.
